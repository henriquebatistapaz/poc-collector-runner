# Canonical SDDs for this Project

This directory holds feature specs in SDD (Software Design Document) format — the source of truth for functional and technical requirements.

## How to use

**One directory per spec** — all artifacts of a feature live together:

```
docs/sdd/
├── constitution.md · TEMPLATE.sdd.md · INDEX.md · README.md    (shared, root level)
├── usage.log                   project-level AI usage: /ai-init setup, /retro, /metrics, /tech-debt
└── specs/
    └── <YYYYMMDD>-<kebab-slug>/    e.g. 20261106-oauth-authentication/
        ├── spec.md                 the SDD (follows TEMPLATE.sdd.md)
        ├── test-plan.md            generated by /test-plan
        ├── usage.log               AI usage per run, one appended line:
        │                           `<ISO datetime> | <prompt> | model: <model> | in: ~<tokens> | out: ~<tokens>`
        └── ...                     feature diagrams, ADRs, anything spec-scoped
```

**Directory name:** `<YYYYMMDD>-<kebab-slug>` — the creation date (`date +%Y%m%d`) followed by a short kebab-case name. The date sorts specs chronologically and is never changed afterwards: approving, shipping or reopening a spec does not rename its directory (that would break links in issues, PRs and usage logs). Two specs on the same day are told apart by the slug. Incidents follow the same rule: `<YYYYMMDD>-incident-<slug>/`.

Older projects used `docs/sdd/<name>/spec.md` directly; `update.sh` / `update.ps1` move those into `specs/` with the date of the spec's first commit (or the file's modification date when it was never committed), and the automation gate still accepts the old path during the transition.

1. Create `docs/sdd/specs/<YYYYMMDD>-<kebab-slug>/spec.md` following the template (from an issue, use `/spec-from-issue` — it does this for you).
2. Register every SDD in `INDEX.md`, linking `specs/<YYYYMMDD>-<kebab-slug>/spec.md`.

Specs do NOT get a prompt file each — the cycle prompts (`/test-plan`, `/implement-spec`, `/validate-implementation`, `/open-mr`) take the spec path as input. Dedicated prompts in `.github/prompts/` are reserved for recurring procedures (runbooks, deploy guides).

## Principles

The project's immutable rules live in `constitution.md` — every SDD must honor them.

## Minimum conventions

- Context and problem
- Goals and out of scope
- Functional and non-functional requirements
- Architecture and decisions
- Implementation plan
- Acceptance criteria (verifiable)
- Risks and rollback
